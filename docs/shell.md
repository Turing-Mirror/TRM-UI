# 桌面壳

`src-tauri/`。这一份记的是**为什么这么写**，代码里的注释记的是每一处的来历。

## 启动顺序

顺序本身是有讲究的，别随手调（`lib.rs::run`）：

```
1. paths::product_root()      解析产品根
2. paths::ensure_user_dirs()  建 User_Data
3. logging::init()            起日志          ← 必须在这里，不能更晚
4. config::read()             读配置
5. i18n::init()               起壳侧翻译      ← 托盘菜单要用
6. register_uri_scheme        注册 trm:// 协议 ← 必须在建窗之前
7. WebviewWindowBuilder       建窗
8. place_on_active_monitor    摆到光标所在屏
9. round_corners              圆角 + 最大化钳制 + 厚框
10. report_and_rescue         记状态，顺手把跑丢的窗口捞回来
11. tray::install             托盘
12. 两个看门狗
```

第 3 步不能更晚：日志起来之前出的任何问题都不会留下记录，而「启动就崩」恰恰是
最需要记录的那一类。

第 6 步不能更晚：窗口的 URL 用的就是这个协议，注册在后面等于让窗口去加载一个
还不存在的 scheme。

## 无边框窗口（Windows）

这一块的每一条都对应一个具体的翻车现场。

### 圆角

Win11 走 DWM 的 `DWMWA_WINDOW_CORNER_PREFERENCE`。**不要**改成「透明窗口 + CSS
圆角」—— 那要把窗口设成 transparent，于是系统投影一起没了，四角还会露出锯齿边
（WebView2 不做窗口级抗锯齿），拖动缩放时角上还会闪。

Win10 上这个属性不存在，`DwmSetWindowAttribute` 会返回错误码。这时退到
`SetWindowRgn` 自己裁圆角 —— 硬边、没有抗锯齿，所以半径取小一点（8px）。
区域按像素算，**窗口一改尺寸就得重套**，所以 `Resized` 事件里要再调一次。

DWM 那条走通的机器上绝不能再去裁一刀：等于拿硬边盖掉系统画好的抗锯齿圆角。

### 投影

投影的来源是窗口样式里的 `WS_CAPTION`，**不是** tao 的 `set_shadow(true)`。

这一处曾经搞反过。tao 的 `set_shadow(true)` 对无边框窗口做的是
`DwmExtendFrameIntoClientArea` 留 1px 边距，那 1px 由 DWM 自己画，看上去就是
那条「Aero 白边」。当时得出的结论「无边框就不能有投影」对 tao 成立，对 Windows
不成立。加上 `WS_CAPTION`，系统就照常画投影、照常做最小化/还原动画，标题栏
本身不会露出来 —— 因为 `WM_NCCALCSIZE` 一律把客户区撑满整个窗口。

VS Code 和 Windows Terminal 走的都是这条路。

### 最大化

尺寸在 `WM_WINDOWPOSCHANGING` 里**落地前**钳到工作区，不是事后
`SetWindowPos` 去改。

事后改的后果：系统已经把新尺寸写进了 `rcNormalPosition`，于是还原矩形变成了
工作区本身 —— 窗口卡在工作区大小，拖边也缩不回最大化前的尺寸。

只拦「过大」的提案（`size_overflows_work`）。还原到最大化前的小矩形必须原样通过。

`WS_THICKFRAME` **永远不要按最大化状态开关**。它是拖边缩放的隐形命中区，摘掉
之后拖边直接失效。

### 那条竖带

`WM_NCCALCSIZE` 在 `wparam != 0` 时直接 `return 0`，**不调** `DefSubclassProc`。

只要 `DefSubclassProc` 跑了，tao 就会按「有边框」把客户区四周内缩一圈（Win10 上
左右下各 8px）。那圈非客户区 WebView 不铺、没人画，窗口一移动系统重画框架就把
旧像素钉在左缘 —— 就是「拖动之后出现、再也不消失的竖带」。

代码里有两段注释写着「这里曾经有 X，别再写回来」：

- `kill_undecorated_shadow_inset_deferred` —— 另起线程等 WebView2 渲染器就绪再
  翻 shadow 标志，为的是达成同一件事。`WM_NCCALCSIZE` 直接拦下就不需要它了，
  而它引入过「工具窗口永久白屏」。
- `force_repaint` —— 用 `RDW_UPDATENOW` 同步重画。那是**跨进程**同步等待
  （WebView2 的渲染窗口不归我们这个线程管），对方还在初始化时两边互相等，
  UI 线程当场死锁。而且它压根没治好那条竖带。

## 窗口跑丢了

「看不见窗口」从外面看是一句话，里面至少是三件事：窗口没建起来、建起来但是
隐藏的、可见但开在了用户看不到的那块屏上。三者修法完全相反，而用户手上只有
「看不见」—— 所以先让窗口自己把状态写进日志。

最难自己发现的是第三种。Tauri 的 `.center()` 永远居中在**主显示器**，而多显示器
的人正在看的往往不是主屏。窗口和它的任务栏按钮一起去了另一块屏，用户这头一点
动静都没有，和「根本没启动」长得一模一样。

判定「跑到屏幕外」用**相交**而不是包含：窗口被拖到屏幕边缘露出一半是用户自己
摆的，把它挪回中间只会更烦人。

`rescue()` 是补救不是例行维护 —— 它会 `show()` 一扇用户可能是故意藏起来的窗口。
只在有理由相信「窗口不见了不是用户的意思」时调用。

## 两个看门狗

| 看门狗 | 抓什么 | 怎么判 |
| --- | --- | --- |
| 白窗（12 秒） | 界面没跑起来 | `ui_ready` 命令有没有被调过 |
| 主线程（15 秒轮询） | 窗口冻住 | 从普通线程 `run_on_main_thread` ping |

白窗那条同时把「UI 从哪儿来的、处理了几个资源请求、404 了几次」写进日志：
**「0 个请求」和「12 个请求、1 个 404」是完全不同的两个 bug**，前者是协议没接上，
后者是某个资源缺了。

12 秒后无条件记一次窗口状态，但**只有界面没报到时才动窗口**。`rescue` 里含
`show()`，用户在这 12 秒里主动把窗口收进托盘的话，无条件救援会让它自己蹦出来。

主线程那条的价值在于**日志里有没有它**：戛然而止且没有这几行 → 事件循环停了，
问题在 Rust 侧；一直在出 → 壳是活的，卡住的是 WebView。

## 界面资源

界面走自定义协议 `trm://`，不走 Tauri 内置的 asset handler。这样 exe 旁边的
`frontend/` 目录就能替换掉随包发布的那份，不用重编译 exe。

解析顺序：外部目录 → 编译期打进二进制的那份。

Windows 上 WebView2 根本不能注册非标准 scheme，所以 wry 把 `trm://localhost/x`
改写成 `http://trm.localhost/x` 再拦截。建窗时的 URL 要分平台写，对不上就是
CSP 拦截，表现为白屏。

打包产物里必须去掉 `crossorigin`（见 `vite.config.ts`）：自定义协议下带着它会
让脚本取不到，整窗白屏，而且控制台里什么都看不到 —— 那时候连脚本都没跑起来。

路径安全：`percent_decode` 必须在 `safe_rel` **之前**跑。反过来的话
`%2e%2e%2f` 能通过检查，然后由文件系统替攻击者完成目录穿越。

## 配置

- **原子写入**：临时文件 + rename。中途断电不会留半份 JSON。
- **坏文件留档**：解析失败时改名成 `.json.bad`，不覆盖。用户可能只是改错了一个
  字符，手工救得回来；覆盖掉就真没了。
- **默认值补齐**：升级新增的键用默认值填，不读出 null。少一个默认值，那一项在
  新装的机器上就是空的，而空和「用户特意清掉了」长得一模一样。
- **浅合并**：深合并会让「把某个对象清空」无法表达。

配置放 `User_Data/`，不放产品目录 —— 升级安装会覆盖产品目录，用户数据放进去
就会在某次更新后凭空消失。

## 开机自启

走注册表 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，不用
`tauri-plugin-autostart`。值指向 `current_exe()`，用户覆盖安装到哪儿，自启就
跟到哪儿。

**状态以注册表为准，不写进配置文件。** 配置是产品语义的真相来源，自启是这台
机器的行为。混在一起的话，把配置拷到另一台机器就会看到「显示开着但实际没自启」。

`VALUE_NAME` 一旦发布就不要再改：改掉之后老的那条留在注册表里没人清理，而新
名字下什么都没有 —— 用户既失去了自启，又多了一条指向旧 exe 的死记录。

## 托盘

左键点图标是「打开窗口」，菜单只走右键。

`TrayIconEvent::Click` 对每个按键都会触发，右键也不例外。而 Windows 上右键菜单
是一个由隐藏消息窗口拥有的弹出菜单：菜单还在的时候去 focus 另一个窗口，系统会
立刻把它收掉 —— 表现就是「右键菜单闪一下就没了」。所以**只认左键、只认松开**。
同时匹配 Down 的话，一次点击会触发两遍。

`close_to_tray` 默认是 `false`。一个点了 X 却不退出的程序，用户会以为它已经关了，
然后在任务管理器里发现它还在 —— 那是背着人跑，不是贴心。要改成常驻的产品必须
在界面上说清楚。

## 在 macOS / Linux 上开发

Windows 专属的部分都在 `#[cfg(windows)]` 里，非 Windows 平台上编译成空函数。
所以 `cargo check` / `cargo test` 在 macOS 上是能跑的，窗口也开得出来 —— 但
**圆角、最大化钳制、开机自启这三件事在别的平台上什么都不做**，只能到 Windows
上验。

`autostart` 的单测按平台分了两条：Windows 上跑真注册表 roundtrip，其他平台上
只验「桩要诚实报错，不许假装写成了」。不要写一条在开发机上长期红着的测试 ——
久而久之「那条本来就红」会变成默认，真红了也没人看。
